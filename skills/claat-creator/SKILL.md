# claat 手順書ワークフロー

素材から `manual.md` を書き起こし、lint を通して HTML にするまでを担当する。読者は「その分野をまったく知らない中学生」だと想定する。読者が途中で手を止めずに最後まで到達できたら成功で、それ以外はすべて失敗と考える。

## 全体の流れ

```text
素材 → 執筆(§1-4) → 日本語チェック(§5) → lint(§6) → HTML 生成(§7) → 報告(§8)
                ↑                                  │
                └───── 本文を書き足す必要が出たら ──┘
```

順序を入れ替えない理由がそれぞれにある。

- **日本語チェックは lint より先。** 日本語を直すと行がずれ、画像の相対パスや `Duration` の位置が壊れることがある。逆順にすると通ったはずの lint をもう一度落とす
- **lint は build より先に単独で回す。** `build` は lint に落ちた時点で止まるので、診断を先に全部見てまとめて直したほうが往復が減る

工程を頭から始めるとは限らない。手元にあるものを見て入口を選ぶ。

| 手元にあるもの | 入口 |
| --- | --- |
| 素材だけ（ソース、README、メモ、URL） | §1 から |
| `.md` がある（書きかけを含む） | まず §6 の lint で現状を把握する。診断を見てから、直しで済むか書き直しかを決める |
| `.md` があり lint が通る | §7 で HTML を生成する |
| HTML まであるが内容を直したい | 直すのは `.md`。生成物は触らない（→ §9） |

分からなければ `.md` の有無を確認し、あれば lint を 1 回回す。診断は現状把握として最も安く、最も情報が多い。

## 1. 素材を読む

対象ディレクトリや資料が示されていなければ、先に聞く。示されたら `README`、エントリポイント、設定ファイル、既存ドキュメント、`package.json` のようなタスク定義を優先して読む。

ここで決めるのは一つだけ。**この手順書に書いてよい事実は何か**。

- 素材から確認できたコマンド・パス・バージョン・出力だけを書く
- 確認できないものは書かない。書きたければユーザーに聞くか、「（未確認）」と明示して下書きに残す
- 推測したコマンドを 1 行混ぜると、読者はそこで詰まって手順書全体を信じなくなる。手順書の価値は正確さの上にしか乗らない

## 2. 読者と到達点

冒頭で次の 3 つを言語化してから書き始める。書けないなら素材が足りない。

- **読者**: 何を知っていて、何を知らない人か
- **到達点**: 最後まで進むと、何ができる状態になるか
- **前提**: 手順に入る前に揃っている必要があるもの（機材、アカウント、インストール済みのもの）

前提と手順を混ぜない。「前提」は読者が事前に用意するもの、「手順」はこの文書の中でやることで、混ざると読者は自分がどこにいるか分からなくなる。

## 3. 手順に割る

**1 手順 = 1 つの、確かめられる状態変化**。これが割り方の唯一の基準になる。

読者はどの手順の終わりでも作業を中断できる。だから各手順の終わりには「今こうなっていれば成功」と分かる状態が必要で、それが書けない単位は手順として大きすぎるか小さすぎる。

- 大きすぎる例: 「環境を構築する」（どこまで進めば成功か分からない）
- ちょうどいい例: 「Go をインストールして `go version` が表示されることを確認する」
- 小さすぎる例: 「ターミナルを開く」（それ単独で確認する状態変化がない）

最初の手順は必ず「ゴールと前提の確認」にする。読者は自分が正しい文書を開いたのか不安なまま読み始めるので、まずそれを解消する。最後の手順は「できたことの確認」と連絡先にする。

`Duration` は割り方が正しいかの検算に使う。ある手順が 15 分を超えるなら、たいてい 2 つ以上の状態変化が混ざっている。実際にかかる時間を素直に見積もり、`0:05:00` のような切りのいい値で埋めない。

## 4. 書く

雛形は `assets/template.md`。そのままでも lint は通るので、出力先にコピーしてから中身を置き換えていく。`id: replace-me` と各見出し・本文は必ず書き換える（説明文をそのまま残さない）。`environments` は `Web`、`status` は指定がなければ `Draft` のままでよい。

**入力規約は §6 の診断表が唯一の台帳になる。** 書きながら迷ったらそこを見る。特に踏みやすいのは次の 3 つで、これだけは書く前に頭に入れておく。

- `Duration` は `H:M:SS` の 3 区切り必須（`5:00` は落ちる。`0:05:00` と書く）
- `##` の直後の最初の非空行が `Duration`。コードフェンスを先に置かない
- 手順の本文がコードブロックだけだと落ちる。コードの前に必ず 1 行、地の文を置く

### 4-1. 中学生に通じる文の条件

読者が詰まる原因は語彙ではなく、**書き手が省略した文脈**にある。次を守る。

| 原則                               | 理由                                                                                            |
| ---------------------------------- | ----------------------------------------------------------------------------------------------- |
| 一文に動作は一つ                   | 二つ書くと読者はどちらを先にやるか判断させられる                                                |
| 「どこで」を先に書く               | 「ターミナルで、次を実行します」。場所が分からないまま動詞を読むと手が止まる                    |
| 専門語は初出のその場で言い換える   | 用語集に飛ばすと読者は戻ってこられない。「CFW（3DS で非公式ツールを動かせるようにする仕組み）」 |
| 操作の後に「こうなれば成功」を書く | これがないと読者は失敗に気づけないまま次へ進む                                                  |
| 「それ」「ここ」を使わず名前で指す | 画面上のボタン名やファイル名をそのまま書く                                                      |
| 敬体（です・ます）で統一する       | 途中で常体に落ちると別人が書いたように読める                                                    |

### 4-2. コードをいつ入れるか

判断基準は一つ。**読者がそのとおりに再現しなければならないものか**。再現するものはコードブロックに入れ、説明は地の文で書く。

| 用途                 | 書き方                                                                                                                 |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 実行するコマンド     | ` ```console ` に 1 行 1 コマンド。`$` や `>` のプロンプト記号は付けない（読者がコピーして貼るときに邪魔になる） |
| ファイルに貼る内容   | ` ```go ` のように言語名を付ける。直前の地の文でファイルのパスを言う                                                 |
| 画面に出るはずの出力 | ` ```text `。読者が照合するためのものなので、実際に出た文字列をそのまま載せる                                        |
| 全体像・構成図       | ` ```text ` の中に矢印で描く。図を作るより速く、あとで直しやすい                                                     |

長いファイルを丸ごと貼らない。変える行と、その前後 2〜3 行だけを見せる。読者が探すのは差分であって全文ではない。

**未検証のコードを載せない。** 素材から確認できないコマンドは、それらしく書けてしまうぶんだけ危険で、読者はそこで詰まる。

### 4-3. 画像・スクリーンショットをいつ入れるか

画像の仕事は 2 つしかない。**「どれを押すのか」を示すこと**と、**「これで合っているか」を照合させること**。この 2 つ以外は入れない。

**入れる**

- GUI の操作対象を、名前だけでは特定できないとき（アイコンだけのボタン、同じ名前が複数ある場合）
- 「正解の見た目」を読者に照合させたいとき（設定画面が正しく開けているか、など）
- 手順どうしの関係を先に見せたいとき（→ ただしこれは ` ```text ` の図で足りることが多い）

**入れない**

- コマンド、パス、設定値、エラーメッセージ。画像にするとコピーできず、検索にも引っかからなくなる。読者にとって害になる
- 装飾目的の画面写真。読者は「これは何を見ろということか」で止まる

**撮り方と書き方**

- 操作に必要な範囲だけを撮る。デスクトップ全体は撮らない
- 個人情報、トークン、社内ホスト名はマスクする
- 保存先は `manual.md` と同じ階層の `images/`。参照は相対パス `![...](images/step3-settings.png)`
- alt テキストには「写っているもの」ではなく**読者に確認してほしいこと**を書く。`![設定画面](images/a.png)` ではなく `![「詳細設定」タブが選ばれている状態](images/step3-settings.png)`

**画像がまだ無いときは、そのパスを書かない。** lint は相対画像の実在を確認するので、後から貼るつもりのパスを書くとビルドが止まる。代わりに、文書とは別に**撮影依頼リスト**をユーザーへ提示する。

```text
撮影をお願いしたい画面（撮れたら images/ に置いてください）
- images/step3-settings.png : 「詳細設定」タブを開いた状態
- images/step5-result.png   : ビルド成功時のターミナル表示
```

### 4-4. claat が解釈する記法（実際に生成して確認済み）

素の Markdown に加えて、claat は次を解釈する。使うと読者の助けになるが、使わなくても手順書は成立する。

**注意ボックス。** claat のパーサー README にある `Positive` と `: 本文` を 2 行で書く形は、**このワークフローが固定している claat のバージョンでは効かない**。`<p>Positive : 本文</p>` という素の段落になる。次のどちらかを使う。

```text
> aside positive
> 時短のコツやベストプラクティスを、緑の枠で出します。

> aside negative
> 警告や、やってはいけないことを、赤い枠で出します。
```

HTML を直接書いても同じ結果になる。

```html
<aside class="negative">
警告や、やってはいけないことを、赤い枠で出します。
</aside>
```

**ダウンロードボタン。** `<button>[Download SDK](https://example.com)</button>` はボタンとして描画される。

**チェックリスト見出し。** `### What you'll learn` `### What we've covered` `### Frequently asked questions` の下の箇条書きは、チェックリストとして描画される。ただしこの判定は**英語の見出し文字列そのもの**に対して行われるので、`### 学ぶこと` のような日本語見出しでは効かない。日本語の手順書で使いたければ見出しだけ英語にすることになるが、読者にとっては普通の箇条書きでも十分伝わる。見出しを英語にしてまで使う価値があるかは内容で判断する。

表、リンク、リストは通常の Markdown どおり。

## 5. 日本語チェック（lint より先に必ず）

書き上げた時点の日本語は、たいてい「同じ鋳型の反復」と「翻訳調」を含んでいる。自分では気づけないので、機械に検出させる。

1. `Duration:` 行を空行に置き換えたコピーを作る。`Duration:` は 1 文書に何十回も出るため、そのままだと `repeated_sentence_lead` の誤検知で本当の指摘が埋もれる（実測で 32 件対 11 件）。行番号は元ファイルと一致させたいので、削除ではなく空行に置き換える。

   ```console
   sed 's/^Duration:.*$//' manual.md > .prose-check.md
   ```
2. `natural-japanese` skill を quick モードで呼び、`.prose-check.md` を対象にする。文書タイプは「社内ガイド・マニュアル」、ジャンルは `tech` を指定する。Windows で出力が文字化けするときは `PYTHONIOENCODING=utf-8` を付ける。
3. finding は「疑いの提示」であって修正指示ではない。**一件ずつ「直した」か「残す（理由）」かを判断して記録する。** 手順書では次の判断がよく出る。

   - 「次のように〜」「〜と表示されます」のような**定型の反復は残す**。手順書では文の型を揃えることが読者の負荷を下げるので、多様性のために崩すと読みにくくなる
   - **一文が長い、動作が二つ入っている、係り受けが遠い**は直す。4-1 の原則に直結する
   - **翻訳調・禁止語**（「〜することができます」「〜と言えるでしょう」）は直す。手順書では冗長なだけで情報を足していない
4. 直したら元の `manual.md` に反映し、`.prose-check.md` は消す。

## 6. lint を通す

lint 本体 `cmd/claat-tools/main.go` はこの skill に同梱されている。**この SKILL.md と同じディレクトリからの相対パス**なので、実行時は skill ディレクトリの絶対パスに置き換える。標準ライブラリだけに依存し `go.mod` も要らないため、**作業ディレクトリはどこでもよい**（ユーザーのプロジェクトが別モジュールでも動く）。2 回目以降は Go のビルドキャッシュが効く。

```console
go run <skill>/cmd/claat-tools/main.go lint path/to/manual.md
```

終了コード 0 になるまで直す。

| コード | 意味 | 次にやること |
| --- | --- | --- |
| 0 | 成功 | §7 へ進む |
| 1 | 入力の lint エラー | 診断を読んで直す（下記） |
| 2 | 実行環境の問題 | `claat` が PATH に無い、引数が不正、ファイルが読めない、UTF-8 でない |
| その他 | `claat` 自身の失敗 | `claat` の標準エラー出力をそのまま読む |

1 と 2 を混同しない。1 は文書を直す話で、2 は環境を直す話になる。

ただし `go run` 経由ではシェルが受け取る `$?` は**失敗なら常に 1 になる**（Go が本来の終了コードを `exit status N` として標準エラーに出し、自分は 1 で終わるため）。`$?` で分岐せず、標準エラーの最終行を読んで判断する。`claat was not found in PATH` のように、2 の場合はメッセージが環境の話だと明示している。

診断は `path:line:column: error CODE message` の形で標準エラーに出る。

```text
dev/manual.md:12:1: error STEP002 expected `Duration: H:M:SS` immediately after the step heading
dev/manual.md:48:5: error ASSET001 local image not found: images/setup.png
```

**直し方の原則: lint を黙らせるために内容を消さない。** `ASSET001` を消すために `![...]()` の行を削るのが最も安易で最も損な直し方になる。読者はその画像を必要としていたから、そこに置かれていた。エラーは「画像を用意しろ」という指示であって「参照をやめろ」ではない。

| コード | 意味 | 判断 |
| --- | --- | --- |
| `META001` | 必須メタデータが無い | 値を決められるものだけ埋める（`status` は `Draft`）。`summary` `feedback link` `analytics account` は勝手に決めず聞く |
| `META002` | 未知キー、または重複キー | 直す。7 キー（`summary` `id` `categories` `environments` `status` `feedback link` `analytics account`）以外は使えない。`tags` や `authors` を足すとここで落ちる。重複は片方を消す前に、どちらの値を残すか確認する |
| `META003` | 値が不正 | 直す。`id` は `[A-Za-z0-9][A-Za-z0-9_-]*`（日本語もスラッシュも使えない）、`environments` は `Web` / `Kiosk`、`status` は `Draft` / `Published` / `Deprecated` / `Hidden` |
| `DOC001` | `#` タイトルが無い / 複数ある / 位置が不正 | 直す。`#` は 1 つだけで、それより前はメタデータ領域（`key: value` 以外の行を置けない）。2 つ目以降の `#` はたいてい `##` の書き間違いなので降格させる。ただし降格すると手順が 1 つ増えるので、直した内容を報告する |
| `STEP001` | `##` が無い、または見出しレベルが不正 | 直す。`#####` `######` は `####` までに繰り上げる |
| `STEP002` | `Duration` が無い / 位置が不正 / 形式が不正 | 直す。`H:M:SS` の 3 区切り必須で `5:00` は通らない。`##` の直後の最初の非空行に置く（コードフェンスを先に置かない）。値が無い手順は、内容から所要時間を見積もって提案し、確認をとる |
| `STEP003` | 手順の本文が空 | **書き手に返す。** ただし本文がコードブロックだけの場合は lint の仕様であり（フェンス内は本文と数えない）、コードの前に地の文を 1 行足せば直る |
| `MD001` | コードフェンスが閉じていない | 直す。どこで閉じるべきかは前後の文脈で判断する。開始行が診断に出るので、そこから読む |
| `ASSET001` | 相対画像が存在しない | **参照を消さない。** パスの綴り違いなら直す。ファイル自体が無ければ、どの画面を撮って `images/` のどこに置いてほしいかを添えてユーザーに依頼する |

本文を大きく書き足す必要が出たら、それは変換ではなく執筆の仕事になる。§4 に戻り、§5 の日本語チェックも通してから §6 に戻る。

## 7. HTML を生成する

HTML 化そのものは PATH 上の `claat` に委譲する。**インストールが要るのはこれだけになる。**

```console
claat version
```

無ければ、検証済みバージョンを入れる。

```console
go install github.com/googlecodelabs/tools/claat@v0.0.0-20240220115335-873fe39d02dc
```

lint が通ったら生成する。

```console
go run <skill>/cmd/claat-tools/main.go build -output output path/to/manual.md
```

`build` は内部で同じ lint を先に回す。成功すると `claat` が `ok<TAB><id>` を出し、出力はメタデータの `id` を使った名前で作られる。

```text
output/
└── <id>/
    ├── index.html
    └── codelab.json
```

出力先の既定は `output`。`-output`（短縮 `-o`）で変えられる。**既存ファイルは消されない**ので、`id` を変えて作り直すと古いディレクトリが残る。不要なら消すのは実行した側の責任になる。

生成後は `index.html` が実際にできていることを確認してから報告する。lint が通っても `claat` 側で失敗すれば終了コードは `claat` のものになる。ローカルで見た目を確認したい場合は `claat serve` が使える。

## 8. 報告する

次の 3 つが揃って完了になる。ひとつでも欠けているなら「できました」と言わない。

1. lint が終了コード 0
2. `output/<id>/index.html` が実在する（HTML まで頼まれている場合）
3. 残っている宿題が一覧でユーザーに伝わっている

3 は特に落としやすい。次を漏らさず伝える。

- 生成された `index.html` と `manual.md` のパス
- lint で直した箇所（何を、なぜ直したか）
- 未撮影の画像（どの画面を、どのパスに置いてほしいか）
- 素材から確認できず「未確認」のまま残した記述
- ユーザーにしか決められなかったメタデータ（`summary` の文言、`feedback link`、`analytics account`）

頼まれていなければ、生成物のコミットも公開もしない。

## 9. 進め方の原則

**生成物を編集しない。** `output/<id>/index.html` は毎回作り直される。ここを直しても次のビルドで消えるうえ、`.md` と HTML の内容が食い違ったまま気づけなくなる。**直す対象は常に `.md`** で、HTML は確認のために開くだけにする。`id` を変えたときは、古い出力ディレクトリを消すかどうかをユーザーに確認する。

**画像で止まらない。** 画像が揃うまで工程全体を止めるのではなく、画像を必要としない範囲を全部先に通す。`.md` を書き上げ、日本語チェックを通し、画像以外の lint エラーを潰しきったところで、撮影依頼リストを添えてユーザーに渡す。画像が届いたら lint と build を回すだけで済む状態にしておく。

**差し戻しは同じ文書で 2 往復まで。** 3 往復目に入るなら、原因はたいてい文書ではなく別のところにある。素材が足りていない、`claat` の環境が壊れている、そもそも書こうとしている手順が確定していない、のいずれかが多い。同じ診断コードが 2 回続けて出た場合も同じ扱いで、回数を重ねるより、何が分かっていないかをユーザーに返したほうが早い。
